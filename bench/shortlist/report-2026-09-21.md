## The corpus fell short of thirty, and that is the finding that matters most

The ticket asked for at least thirty file-localisation questions drawn from real recorded turns
in `.tofu/sessions`. **The corpus holds four.** `.tofu/sessions` currently carries 131 recorded
turns (73 turn directories plus 58 standalone turn files). Of those, 20 ever call `edit` or
`write`, meaning 20 is the entire population of turns where a file actually changed. Of those 20:

- **12 are file creation, not localisation.** `hello.txt` (x5), `notes.txt` (x3), `notes.md`
  (x1), `.local/boji-tests/boji-write-test.md` (x1), plus 2 more single-file creation turns: the
  task is "write a new file," there is no existing file to retrieve, and `file_shortlist` does
  not apply. Rejected: not a localisation question.
- **5 are exact duplicates of one canonical turn.** `turn-18d6a27c7dfb1644`,
  `turn-18d6a74abeb9c3ec`, `turn-18d6a7e466fbd038`, `turn-18d6a80dc5d90f84`,
  `turn-18d6a8b2205e4268` carry byte-identical task text, the same model (`claude-opus-5`), and
  the same starting repository as `turn-18d6a7961d933ee8`, run minutes apart. They are reruns of
  one real turn, not five independent ones. Rejected: duplicate of a turn already in the corpus.
- **2 touched too many files with no single answer and no textual tie-breaker.**
  `turn-18d6913a528f4528` (outcome `error`) and the accepted Hono-build turn
  `turn-18d69bfed2bf52a0` (5 files: `src/app.ts`, `src/index.ts`, `src/store.ts`,
  `src/app.test.ts`, `package.json`) build a feature from nothing; most of the files each touches
  did not exist before the turn, so there is no pre-existing tree to localise against. Rejected:
  new-file creation dominates the edit set.
- **1 turn, decomposed, is what is left.** `turn-18d6a7961d933ee8` (outcome `stopped`) is a
  seven-item numbered spec against an already-built six-file repo. Four of its seven items name
  their target file in the task text itself, confirmed against the turn's own real `write` calls:
  item 3 ("the filtering belongs in the storage code") to `src/store.ts`; item 6 ("update
  README.md") to `README.md`; item 7 ("add a check script to package.json") to `package.json`;
  item 5 ("move validation into its own file under src") is excluded, because `src/validation.ts`
  did not exist before this turn and cannot be a retrieval target. Items 1, 2 and 4 touch multiple
  files each with no single correct answer and are excluded for the same reason as the Hono-build
  turn. The fourth corpus row is the whole task, scored against the set of files it touched that
  already existed (`src/app.ts`, `src/store.ts`, `src/app.test.ts`, `README.md`, `package.json`,
  `tsconfig.json`), again excluding the new `src/validation.ts`.

That is 4 questions, all four traced to real bytes: real task text lifted verbatim from one
recorded turn, real file content lifted verbatim from that turn's own `write` calls and from the
`write` calls of the turn that built the repository it started from. Nothing here is authored or
guessed. **It is also an order of magnitude short of the acceptance line, and no amount of
rereading `.tofu/sessions` changes that: the session log on this machine has been used almost
entirely for read-only "explain this repo" turns, and the few coding turns it has are either
brand-new-file creation or five copies of one multi-file spec.** The corpus needs thirty
independent real edit turns to reach the ticket's bar. `.tofu/sessions` does not have them yet.
Getting there means recording thirty more real coding turns first, which is a usage fact, not
something this ticket can produce.

Every arm below is real code, tested and measured; the verdict itself has to be read as
directional, from n=4, not as a settled number.

## The four arms, on the identical four questions

Shortlist size: **5**, the same number feeding the reranked arm and the unreranked one
(`ShortlistSize` in `bench/shortlist/arm.go`). All four candidate trees hold 7 files, so a
shortlist of 5 already drops two of the weakest BM25 candidates before the judge or the
unreranked baseline ever sees them.

| Arm | hit@1 | hit@5 |
|---|---|---|
| grep (weak free) | 1/4 (25.0%) | 3/4 (75.0%) |
| BM25 (strong free) | 1/4 (25.0%) | 4/4 (100.0%) |
| shortlist alone, unreranked (BM25 top 5, no judge) | 1/4 (25.0%) | 4/4 (100.0%) |
| judged, Jev reranking the BM25 shortlist | **4/4 (100.0%)** | 4/4 (100.0%) |

BM25 and the unreranked shortlist score identically because the shortlist size (5) exceeds the
number of files BM25 must beat to reach 100% hit@5 on a 7-file tree; the interesting number here
is hit@1, where the retrieval alone is 25% and the judge lifts it to 100%.

**BM25 picked `src/app.test.ts` first on all four questions, including the two where it should
have been trivial** (`package.json` for the "add a check script to package.json" question,
`README.md` for the "update README.md" question). The test file is the longest and most
repetitive document in the tree (`describe`, `it`, `Task`, `title`, `expect` recur dozens of
times), and this BM25 implementation has no stopword list and no field weighting, so raw term
frequency in a verbose file beats a short, sparse, exact-match file every time. That is a real
weakness in a from-scratch BM25 over source code, not a corpus artefact: a production
implementation needs either a stopword list or a path/filename boost, and this run is the
evidence for that, not a guess.

**Grep beat BM25 on nothing and lost to it on hit@5** (3/4 against 4/4): the literal-substring
arm missed the `README.md` question outright, because the task text's words (routes, fields,
query filters) appear more densely, again, in `src/app.test.ts`.

## Same question, asked twice

`turn-18d6a7961d933ee8#item3` (the `src/store.ts` question) asked twice, one call each,
sequential:

```
first  top1 src/store.ts (noul 0.63)
second top1 src/store.ts (noul 0.60)
largest noul spread across all 5 candidates: 0.030
```

Same file picked both times. The spread, 0.03, sits inside the 0.02-to-0.05 range bench-001
measured on this same route, and below the 0.05 dead band bench-001's finding 4 recommended. One
rerun is not a distribution; this is one real data point in the direction that route's earlier
measurement predicted.

## A quirk worth carrying forward: the Choice and the Nouls disagreed once

On the whole-task question, the per-candidate Nouls ranked `package.json` highest, a hit, since
`package.json` is in that row's label set, but the single `best` Choice question, asked in the
same call over the same candidates, answered `__none__`. The Noul-based ranking and the
Choice-based pick are not the same signal and can point two different ways in one response. This
implementation scores hit@k off the Nouls, which is why the row still counts as a hit; a design
that reads only the Choice would have missed it. Worth a note for whoever wires this for real:
prefer the Noul ranking over the Choice's single pick, or ask why they disagree before trusting
either.

## Whether the judgment earned the build

**Not yet decided, and it cannot be decided from four questions.** Directionally, on this tiny
run, the judge closed a real gap the strong free arm left open (25% to 100% hit@1) and did so for
about six hundredths of a cent and a third of a second, which matches the shape of the published
number this ticket set out to check (BM25 56.7%, judged 78.9%). But n=4 against a published n=30
is not evidence at the scale the acceptance line asked for, and the strong free arm was actively
weak here for a fixable, unrelated reason (no stopword handling), which the real BM25-vs-judged
gap could shrink once that is fixed. **The honest reading: this run does not clear the bar for
saying "BM25 alone is within a small margin of the reranked arm, do not build it," but it also
does not clear the bar for recommending the build, because four questions cannot clear either
bar.** The next real step is recording thirty independent coding turns, not writing more code
against this same four.
