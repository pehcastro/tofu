## The two arms

| Arm | Result bytes | Rendered bytes | Handle | Source of the number |
|---|---|---|---|---|
| handle, the default | 11,210 | 1,266 | yes | live, the row above |
| truncation, `Config.TruncateResults` | 11,210 | 8,211 | no | arithmetic on `truncateMiddle` at the shipped 8,192 byte cap, plus the 19 byte marker |

The off arm figure is not a live measurement. `truncateMiddle` renders `cap + len(marker)` bytes for any body over the cap, so 8,211 is fixed once the body is over 8,192 and does not depend on this file. `TestTheOffArmCutsTheMiddleAndHandsBackNoHandle` asserts that same 8,211 at the same cap on a different body.

## What this does not say

Billed input tokens per turn with and against handles are still unmeasured. This run has one oversize result in one turn, and the arms were not run against each other on the same task, because the off arm has no command line flag yet: `Config.TruncateResults` is reachable from Go and from `bench/`, and nothing in `cmd/boji` sets it. Until that flag exists the two arms cannot be compared on a live task, and rendered bytes is a proxy for tokens, not tokens.

The 6.5 times figure is the same ratio BOJI-084 measured offline on a 20,020 byte body, which is a coincidence of the cap rather than a confirmation: both arms' sizes are governed by the same 8,192 byte bound.
