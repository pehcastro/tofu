# v4 checklist

Written 2026-09-23, before any arm ran v4. Never edited after seeing a diff. Any change to this file after the first run invalidates every run before it, and the report says so.

Nine items. Each one is decided by `bun bench/harness/task/v4.check.ts <arm-dir>`. This checker starts no server and imports nothing from the arm: it reads `ANSWER.json` and hashes the tree against `bench/harness/task/v4.seed`, which sits beside it.

## What is different about v4

v1, v2 and v3 are all work on code. v4 is the only one where a passing run writes no code at all.

The tree is a service of 48 files and 1,129 lines. One question is asked about it, the answer is in one file, and three things in the tree give the wrong answer plausibly:

- `docs/plans.md` says in as many words that gold carries every export format. It is stale and the README says documentation here is not checked against anything.
- `src/plan/plans.ts` grants gold `everything`, which is true and is not the end of the story.
- `src/legacy/plans.ts` holds a gold tier that allows csv. Nothing imports it.

The answer is in `src/plan/overrides.ts`, which is merged over the plan table by `src/plan/resolve.ts`, and the `formats` field cannot be copied from any single file: it is `src/export/formats.ts` minus what `src/plan/overrides.ts` withholds.

Two accounts are named alike on purpose. `acct_gold_7` is on gold, and `acct_gold_70` is on enterprise, which withholds nothing.

The seed is `bench/harness/task/v4.seed`, identical for every arm.

The checker scores the untouched seed first. That score is the floor, and it is 2 of 9: an arm that does nothing at all still leaves the tree alone.

## The task

`bench/harness/task/v4.prompt.txt`, verbatim, the same string to all three arms.

## Is there an answer

1. `ANSWER.json` is at the top of the project and parses as a JSON object.
2. It carries exactly `status`, `code`, `decided_in`, `symbol` and `formats`, and no other key. The prompt says exactly these five.

## Is the answer right

3. `status` is `403`.
4. `code` is `plan.capability.withheld`.
5. `decided_in` is `src/plan/overrides.ts`, after normalising a leading `./` and any backslash. An arm that names the route, the middleware or the plan table has followed the request to where it was reported rather than to where it was decided.
6. `symbol` is `withheldByPlan`.
7. `formats` is exactly `["json", "ndjson", "parquet"]` in that order. This one cannot be read off a single file and it is the item that says whether the arm understood the merge or recognised a name.

## Was it a reading task

8. Every file in the seed is still present and byte identical. Hashed file by file against the seed that sits beside the checker.
9. No file was added other than `ANSWER.json`. A lockfile from running the suite is tolerated and nothing else is.

## What is recorded but not scored

- `shape:extras`, every path in the arm tree that the seed did not carry. A scratch file, a notes file or a script an arm wrote to answer the question is interesting and is not a failure of the answer.
- `shape:answer`, the file count of the seed and of the arm tree.

## How a run is judged

A run passes when all nine items pass.

The cost side is where this task earns its place, and the checker cannot see it. What an arm read to get the answer is tool calls, tokens in, and turns, and those come from the run row. Two arms that both answer correctly are not equal if one read six files and the other read sixty.
