# v2 checklist

Written 2026-09-19, before any arm ran v2. Never edited after seeing a diff. Any change to this file after the first run invalidates every run before it, and the report says so.

Twenty items. Each one is decided by `bun .playground/v2.check.ts <arm-dir>`, which imports the arm's `src/index.ts` and drives it with `app.request()`, so nothing binds a port and no arm can pass by talking to a server somebody else started. An item the checker cannot evaluate is `could_not_evaluate`, never a pass.

The gates decide whether a run is compared at all. This list decides whether a run did the job. A run that builds, tests clean and misses six of these is a run that changed something else.

## What is different about v2

v1 was a build. Every arm wrote new files and nothing here had a before. v2 is maintenance: the starting tree is that arm's own v1 result, and the task asks for a rename that runs through three files, a field threaded from the wire to the store, a filter pushed down into storage, a constant changed, a function moved, and two existing non-source files brought up to date.

The checker scores the untouched starting tree first. That score is the floor. An arm that scores the floor changed nothing that matters.

## The task

`.playground/v2.prompt.txt`, verbatim, the same string to all three arms.

## Did the old behaviour survive

1. `GET /` still returns 200 with the original body. It is the cheapest thing to break and the second time it is asked.
2. The v1 lifecycle still works end to first read: `POST /tasks` returns 200 or 201 with an id and the title, `GET /tasks/<id>` returns that title, `GET /tasks` contains it, and after `DELETE /tasks/<id>` the read is 404.
3. Invalid input is still refused: `POST /tasks` with `{}` is 400, with `{"title":""}` is 400, and with a body that is not JSON is 400 and not 500.
4. An unknown id is still 404 on `GET`, `PATCH` and `DELETE`, and each of those three bodies parses as a JSON object.

## The rename

5. A created task's JSON carries `completed` and does not carry `done`. Both halves are required: an arm that added `completed` and left `done` beside it did not rename anything.
6. `POST /tasks` with `{"title":"x","completed":true}` returns 200 or 201 and reads back `completed` true.
7. `PATCH /tasks/<id>` with `{"completed":true}` returns 200 and reads back `completed` true.
8. `PATCH /tasks/<id>` with `{"done":true}` returns 400.
9. `POST /tasks` with `{"title":"x","done":true}` returns 400.

## The new field

10. A task created without a priority reads back `priority` `"normal"`.
11. `POST /tasks` with `{"title":"x","priority":"high"}` reads back `priority` `"high"`.
12. `PATCH /tasks/<id>` with `{"priority":"low"}` returns 200 and reads back `priority` `"low"`.
13. `POST /tasks` with `{"title":"x","priority":"urgent"}` returns 400 and the body parses as a JSON object.
14. `PATCH /tasks/<id>` with `{"title":"v2 patch bad priority","priority":"urgent"}` returns 400. The title is in the body on purpose: a body carrying only a priority is rejected by the v1 code for having nothing it recognises, and that is not this item.

## The filters

15. `GET /tasks?completed=true` returns only completed tasks and `GET /tasks?completed=false` returns only the others. Checked against a fixture of four tasks the checker creates itself.
16. `GET /tasks?priority=high` returns only high priority tasks.
17. `GET /tasks?completed=true&priority=high` returns exactly the tasks that are both, which is one of the four.
18. `GET /tasks?completed=maybe` is 400 and `GET /tasks?priority=urgent` is 400.

## The constant

19. A 120-character title is accepted and a 121-character title is 400. The old limit was 200, so an arm that changed nothing fails on the second half.

## Did it leave the place tidy

20. The tests pass by the arm's own command, with the count stated, and at least one test file mentions a query filter or the priority field. A suite that still only covers v1 is a suite that would not have caught items 10 through 18.

## What is recorded but not scored

Three things the prompt asks for and the checker reports without grading, because grading them means guessing at names the prompt never fixed, and that is grading taste rather than behaviour.

- `shape:helpers`, whether the validation code moved to its own file under `src` and the route file imports it. Reported as the list of `src` files and which of them the route file imports.
- `shape:readme`, whether `README.md` now mentions the routes, `completed` and `priority`.
- `shape:check`, whether `package.json` gained a `check` script and what it runs.

Also recorded: whether the arm kept the store in a class or moved to something else, and how many `src` files exist, which tells you whether it edited in place or reorganised under cover of the task.

## How a run is judged

A run passes when all twenty items pass. All twenty are binary and none is a matter of opinion.

Failing any one of them keeps the run out of the time and cost comparison, per `bench-harness.md`: quality is a door, not an axis. The report still shows the run and which item it missed.
