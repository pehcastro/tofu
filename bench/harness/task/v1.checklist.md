# v1 checklist

Written 2026-09-18, before any arm ran v1. Never edited after seeing a diff. Any change to this file after the first run invalidates every run before it, and the report says so.

Twenty items. Each one is decided by `bun .playground/v1.check.ts <arm-dir>`, which imports the arm's `src/index.ts` and drives it with `app.request()`, so nothing binds a port and no arm can pass by talking to a server somebody else started. An item the checker cannot evaluate is `could_not_evaluate`, never a pass.

The gates decide whether a run is compared at all. This list decides whether a run did the job. A run that builds, tests clean and misses six of these is a run that wrote something else.

## The task

`.playground/v1.prompt.txt`, verbatim, the same string to all three arms. A task list API on the seeded Hono server: five routes, in memory, the existing route kept, 400 on bad input, 404 on an unknown id, both with a JSON body, and tests covering success and failure.

## Does it do the thing

1. `GET /` still returns 200 with the original body. The prompt says keep it working and it is the cheapest thing to break.
2. `POST /tasks` with `{"title":"write the report"}` returns 201, or 200, and a JSON body carrying an id and that title.
3. The id from item 2 is usable: `GET /tasks/<id>` returns 200 and the same title.
4. `GET /tasks` returns 200 and an array containing the task created in item 2.
5. `PATCH /tasks/<id>` with `{"title":"renamed"}` returns 200 and the title is changed when read back.
6. `PATCH /tasks/<id>` with `{"done":true}` returns 200 and the done flag is true when read back.
7. `DELETE /tasks/<id>` returns 200 or 204, and a following `GET /tasks/<id>` returns 404.
8. Two `POST /tasks` calls produce two different ids.

## Does it refuse the wrong thing

9. `POST /tasks` with `{}` returns 400.
10. `POST /tasks` with `{"title":""}` returns 400. The prompt says non-empty and an empty string is the case most often missed.
11. `POST /tasks` with `{"title":"   "}` returns 400 or 201, and whichever it is, the same answer for every arm is not required: this item records the behaviour rather than grading it, because the prompt does not say. Recorded, not scored.
12. `POST /tasks` with a body that is not JSON returns 400 and does not return 500.
13. `GET /tasks/<unknown>` returns 404.
14. `PATCH /tasks/<unknown>` returns 404.
15. `DELETE /tasks/<unknown>` returns 404.
16. Every 400 and every 404 above returns a JSON body, parseable, not an empty body and not a plain string. The prompt asks for a JSON error body and this is the item that checks it rather than trusting the status code.

## Did it leave the place tidy

17. The state is in memory: no file appears under the arm's directory that looks like a store, and no dependency was added beyond what the seed declares. Adding a database is not wrong, it is not what was asked.
18. The tests the arm wrote pass, run by their own command, with the count stated.
19. The tests cover at least one failure path. A suite that only tests the happy path is a suite that would not have caught items 9 through 16.
20. `GET /` is still covered or still passing. An arm that deleted the seed's only existing behaviour to make its own tests pass fails here.

## What is recorded but not scored

Item 11, above.

The shape of the id. A counter, a uuid, a random string, all fine. Worth recording because it tells you something about how the arm thought.

Whether the arm wrote one file or several, and whether it split routes from storage. Not graded, because the prompt did not ask, and because grading it would be grading taste.

## How a run is judged

A run passes when items 1 to 10 and 12 to 20 pass. Nineteen items, all binary, none of them a matter of opinion.

Failing any one of them keeps the run out of the time and cost comparison, per `bench-harness.md`: quality is a door, not an axis. The report still shows the run and which item it missed.
