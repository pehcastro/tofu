# v3 checklist

Written 2026-09-23, before any arm ran v3. Never edited after seeing a diff. Any change to this file after the first run invalidates every run before it, and the report says so.

Twenty-two items. Each one is decided by `bun bench/harness/task/v3.check.ts <arm-dir>`, which imports the arm's `src/index.ts` and drives it with `app.request()`, so nothing binds a port and no arm can pass by talking to a server somebody else started. An item the checker cannot evaluate is `could_not_evaluate`, never a pass.

## What is different about v3

v1 and v2 are the same kind of work: change a small API that is already there, against a prompt that says exactly what the result should be. Neither of them has a wrong road to go down.

v3 has one. The prompt asks for expiry and says an expired note must not linger, which reads either as removing the note or as keeping it out of the default listing. One of those readings is much more work, and it is also the one that makes the fourth requirement impossible, because a note that has been deleted cannot be listed by `GET /notes?expired=true`. The tree says the same thing twice more: `docs/decisions.md` of 2026-04-11 says the server never removes a note on its own initiative, and the entry of 2026-03-02 forbids the timer that the delete reading tends to bring with it.

So there is a cheap reading and an expensive one, the tree settles which, and the prompt asks the arm to write down what it chose and why. What separates the arms is not only whether the result works but how much the arm wrote before it found out.

The starting tree is `bench/harness/task/v3.seed`, eleven files and 399 lines, identical for every arm. It is not that arm's v2 result: v3 is a different task with its own seed, not the next version of the hono line.

The checker scores the untouched seed first. That score is the floor, and it is 8 of 22.

## The task

`bench/harness/task/v3.prompt.txt`, verbatim, the same string to all three arms.

## Did the old behaviour survive

1. `GET /` still returns 200 with the body `notes`.
2. The lifecycle still works: `POST /notes` returns 201 with an id and the title, `GET /notes/<id>` returns that title, `GET /notes` contains it, and after `DELETE /notes/<id>` the read is 404.
3. Invalid input is still refused: `POST /notes` with `{}` is 400, with an empty title is 400, with a 121-character title is 400, and with a body that is not JSON is 400 and not 500.
4. An unknown id is still 404 on `GET`, `PATCH` and `DELETE`, and each of those three bodies parses as a JSON object.

## The new field

5. A note created with an `expiresAt` in the future reads back the same instant.
6. `POST /notes` with `"expiresAt": "tomorrow"` returns 400 and the body parses as a JSON object.
7. `POST /notes` with an `expiresAt` in the year 2001 returns 400 and the body parses as a JSON object.
8. A note created without an `expiresAt` is readable and is in `GET /notes`.
9. `PATCH /notes/<id>` sets an `expiresAt` and it reads back.
10. `PATCH /notes/<id>` with `"expiresAt": null` clears it, and the note is still readable after the expiry it used to carry has gone by.
11. `PATCH /notes/<id>` with a title and an `expiresAt` in the year 2001 returns 400. The title is in the body on purpose: a body carrying only an `expiresAt` is rejected by the seed for having nothing it recognises, and that is not this item.

## Which reading was taken

12. Before their expiry, all three fixture notes are in `GET /notes` and the expiring one is 200 on `GET /notes/<id>`.
13. After their expiry, neither expired fixture note is in `GET /notes`, and the note with no expiry at all is still there.
14. After its expiry, `GET /notes/<id>` on an expired note is 404.
15. After its expiry, an expired note is in `GET /notes?expired=true`. **This is the item the expensive reading cannot pass.** An arm that deleted the note on expiry has nothing left to list.
16. `GET /notes?expired=true` puts the note that expired most recently first.
17. `GET /notes?expired=false` carries the live note and neither expired one.
18. `GET /notes?expired=maybe` is 400.
19. A note whose expiry is 150 ms away is 404 three hundred milliseconds later. **This is the item a sweeper cannot pass**, because between two ticks it gives the wrong answer, and `docs/decisions.md` of 2026-03-02 forbids the timer anyway.

## Did it leave the place tidy

20. The tests pass by the arm's own command, with the count stated, and at least one test file mentions expiry. A suite that still only covers the seed is a suite that would not have caught items 5 through 19.
21. `DECISIONS.md` is at the top of the tree, is more than eighty characters, and mentions expiry. This is the sixth requirement of the prompt, and it is the only way a headless run can show that the arm noticed the requirement could be read two ways. An arm that picked without noticing fails this and can still pass everything else, which is the point.
22. `package.json` declares no runtime dependency. `docs/decisions.md` of 2026-05-20 says this service has none and that the build machine has no network, and the prompt's sixth requirement says to follow what is written down.

## What is recorded but not scored

- `shape:timers`, whether any runtime source file mentions `setInterval`, `setTimeout`, `Bun.sleep`, `cron` or `scheduler`. This is the design an arm took, reported rather than graded, because item 19 already grades the behaviour and a file that merely names a timer is not a failure.
- `shape:source`, the list of `src` files, which says whether the arm edited in place or reorganised under cover of the task.
- `shape:decisions`, whether `docs/decisions.md` is still there and how many of its three dated entries survive. An arm that deleted the thing that contradicted it is a result worth seeing.

## How a run is judged

A run passes when all twenty-two items pass. All twenty-two are binary and none is a matter of opinion.

Failing any one of them keeps the run out of the time and cost comparison, per `bench-harness.md`: quality is a door, not an axis. The report still shows the run and which item it missed.

The cost side of this task is the interesting half and the checker cannot see it. How much an arm wrote before it discovered which reading was right is turns, tool calls and lines added, and those come from the run row, not from here.
